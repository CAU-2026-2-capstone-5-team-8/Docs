# 4. 10월 9일 교수 면담과 다음 주 중간발표

작성 2026-10-05. 발표 날짜는 다음 주 중 미정. AI/추천 설계 담당 1명, 팀원은 백엔드 중심이라는 조건이다.
아래 일정은 제안이며 실제 완료 여부는 산출물로 갱신한다.

## 4.1 금요일에 전달할 세 가지

1. **어디까지 했나:** 실제 자료 수집, 진단/채점, 개념 기반 추천, 계정·저장·서재의 연결과 검증.
2. **지금 추천하면 어떻게 되나:** 고정 도서 자료와 명시적인 가상 응답으로 현재 코드의 결과를 재현.
3. **어떻게 개선할 것인가:** 독자 수행과 책의 요구/설명 지원을 비교하고 독립적인 평가로 확인하는 설계.

‘추천 정확도가 검증됐다’는 표현은 사용하지 않는다. 현재 성과인 서비스 통합과 추천 규칙의
재현 가능성, 아직 검증해야 할 적합성을 각각 설명한다.

현재까지 제시할 수 있는 구현 근거:

- 개념 진단·준비도 v2·계정·서재 화면 연결: 병합된 Backend #33/34, ML #38, Frontend #9.
- AI 검토 이력을 구분한 선형대수 후보 18문항: QG #7 / Backend #32. 사람 검토·실측 문항 타당성으로 표현하지 않음.
- 안정화 변경 통합: Backend 238통과/외부 조건부 7제외, Frontend 39통과와 웹 빌드, 실제 인증 연동 45건.
  해당 Backend #35/#36와 Frontend #10은 이 기록 시점에 원격 main 미병합이다.
- [현재 계산 사례](evidence/current-recommendation.md): 83개 역사적 후보 중 11개 개념 연결,
  3개 가상 응답 조건에서 실제 ML 계산. 운영 데이터 수나 실제 사용자 성능으로 제시하지 않음.

이전 검증과 이번 결과의 실행 환경은 같다고 가정하지 않는다. 목요일 시연은 하나의 환경으로 고정한다.

## 4.2 면담용 3분 설명 초안

현재는 사용자가 분야를 고르고 문제를 풀면, 관찰된 개념별 수행과 책의 개념·선수관계를 비교해
추천하고 결과를 저장하는 흐름을 구현했습니다. 책 자료의 출처와 진단 응답을 함께 추적할 수 있습니다.

다만 같은 개념을 다루는 입문서와 심화서를 구별할 근거가 부족하고, 현재 동점 조건에서는
도서 ID로 표시 순서가 결정됩니다. 자동 테스트 통과를 좋은 추천의 증거로 생각하지 않고 있습니다.

그래서 한 분야의 일부 장을 대상으로, 책이 무엇을 가르치고 무엇을 이미 안다고 요구하는지
본문에서 분석하려 합니다. 독자는 읽기 전 수행을 측정하고, 추천의 적합성은 독립적인 읽기 후
과제와 전공 평가자의 판단으로 확인하려 합니다. 모델은 본문 속성 추출을 맡기고, 매칭 근거를
따라갈 수 있게 설계할 계획입니다.

이번 면담에서는 이 범위가 캡스톤의 기여로 적절한지, 전공 검토와 사용자 평가를 어떻게
확보할 수 있을지 의견을 받고 싶습니다.

## 4.3 시연 구성

| 순서 | 보여줄 것 | 반드시 함께 말할 것 |
| --- | --- | --- |
| 1 | 현재 흐름 그림 | 구현된 서비스 경로와 제안 설계는 다름 |
| 2 | 현재 추천 재현 사례의 입력·출력 | 실도서 수집 snapshot + 가상 응답 + 현재 ML 계산 |
| 3 | 같은 책의 준비도·순위 변화 또는 불변 | 변화 자체는 좋은 추천의 증거가 아님 |
| 4 | 부족한 구별 능력 | 동률 조건·미평가·자료 부족과 ID 순위 영향 |
| 5 | 목표 설계 그림과 전/후 문항 설계 | 새 분석/정책은 아직 제안 |

온라인 전체 앱 시연은 목요일에 사용할 코드·DB·bank·포트를 고정한 뒤 다시 확인한다.
오늘의 오프라인 ML 사례를 브라우저→Backend→DB 전체 시연 완료라고 말하지 않는다.
인터넷/서버 장애에 대비해 동일 입력/출력 JSON과 화면을 준비한다. 합성 결과를 실제 사용자로 꾸미지 않는다.

새 학습 모델, 적응형 검사, 새로운 DB 체계, 사진 인식은 이 주의 필수 산출물에 넣지 않는다.

## 4.5 다음 주 중간발표까지

- 면담 피드백으로 연구 질문과 평가 단위를 확정하고 설계 v0.2 갱신.
- 수동 속성으로도 자료 차이를 설명할 수 있는지 확인한 예비 사례 제시.
- 여건이 되면 고정 모델의 속성 추출을 작은 개발 자료에서 시도하고 오류/비용을 기록.
- 실제 전공 검토자·참가자가 없으면 실험 계획과 미확보 상태를 명시.
- 앱 기능을 더 늘리기보다 구현된 기준선, 개선 가설, 검증 절차의 연결을 발표.

모델 실험이 시간 안에 안 되면 현재 코드의 재현 가능한 결과와 수동 속성 비교까지 발표한다.
완료하지 않은 사람 평가나 학습 성능 숫자를 발표용으로 채우지 않는다.

제목에 ‘정확도 향상’은 실제 독립 평가 결과가 생긴 뒤 사용한다.
학습 모델을 훈련하지 않았다면 ‘모델을 학습했다’고 말하지 않는다.

## 4.7 교수에게 물을 질문 (우선순위)

1. 독자 수행과 자료 요구사항을 연결하는 **설명 가능한 추천 + 검증 실험**이 적절한 핵심 기여인가?
2. 책 전체 대신 일부 장/절, 한 분야로 범위를 줄여 평가해도 되는가?
3. 전공 관점에서 책 속성·문항을 검토할 사람이나 참가자 모집을 도와줄 수 있는가?
4. 중간발표는 구현된 기준선과 설계/예비 실험 중심으로 어디까지 보여주면 되는가?
5. 공통 난도 척도의 추정까지 필요한가, 근거 기반 적합성 비교가 현실적인가?

## 4.8 예상 질문과 정직한 답변

- ‘왜 BERT를 바로 쓰지 않나요?’ → 예측할 속성과 정답 기준이 먼저 필요합니다. 고정 모델 추출부터 비교하고 라벨이 쌓이면 분류기 학습을 검토합니다.
- ‘이 추천이 좋다는 근거가 있나요?’ → 현재는 규칙과 서비스 동작을 검증했습니다. 좋은 매칭인지는 고정 목록/현재 정책/새 정책의 독립 비교로 확인할 계획입니다.
- ‘문제를 AI가 만들면 평가도 AI 마음 아닌가요?’ → 측정 목표와 정답 근거를 고정하고 생성·AI 검토·사람 검토·실제 응답을 분리합니다. 아직 사람 검토가 없으면 그 상태를 공개합니다.
- ‘본문 일부로 책 전체를 평가하나요?’ → 첫 주장은 분석한 장/절 범위로 제한합니다. 책 전체로 확장하는 타당성은 후속 과제입니다.
- ‘왜 사용자 수준 점수가 없나요?’ → 서로 다른 문항과 책 분석 점수를 공통 척도로 볼 근거가 부족해 관찰 단위로 제시합니다.
